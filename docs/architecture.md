# 架构设计说明

本文记录票根权益与清算后端的关键设计取舍，重点说明那些“看起来能简单处理、实则必须区分”的规则。

## 1. 事件溯源内核

- 领域事件是各渠道（票务、景区终端、离线同步、申诉、清算）唯一的交换格式，只增不改。
- `EventStore` 按聚合维护单调 `version`（乐观并发），`event_id` 全局幂等，提交为原子批。
- **注入业务时钟**：`new EventStore({ clock })`。所有未显式给出的 `occurred_at` 都取自该时钟，
  而不是进程墙钟。离线合并依赖“发生时间”，若用墙钟，一条后补提交的退票会错误地早于历史核销。
- 读模型由事件折叠重建：
  - `buildReadModel`：当前态；
  - `buildReadModelAt(store, asOf)`：只折叠 `occurred_at <= asOf` 的事件，是离线按发生时间重放的基础。

### 为何要“时点读模型”
离线凭证 10-12 10:00 在断网景区签发，游客 10-12 15:00 赛后退票，10-13 才联网。
合并时必须问：**这笔核销在它发生的那一刻是否合法？** 用 10:00 的模型重放，退票尚未发生，
核销成立；若一笔离线核销发生在 16:00（退票之后），同一机制判 `TICKET_REFUNDED`。

## 2. 政策版本与“按版判定”

- `POLICY_PUBLISHED` 一经发布不可变；新规则是新版本，不是覆盖旧版本。
- 同一 `policy_code` 的生效区间不允许重叠，保证任一时刻只有一版生效。
- 权益在授予时锁定 `policy_id`（`BENEFIT_GRANTED.policy_id`）；窗口在授予时复制一份到账户，
  后续政策修订不影响已授予账户。
- **跨景区是否可重复使用是政策属性，不是核销端的固定行为**：
  - `PER_SPOT`：每个景区权利项独立计数 → 允许跨景区重复使用、同日多点游览；
  - `GLOBAL`：一个全局权利项，所有协议景区合计计数 → 跨景区去重。
- 每次拒绝（`REDEMPTION_REJECTED`）都带 `policy_id` 与 `rule_detail`（引用政策代码、版本、
  窗口/额度/记名/闭园的具体条款），游客可以知道“被哪一版规则拒绝、依据是什么”。

资格判定集中在纯函数 `evaluateEligibility(model, request)`，在线核销与离线合并共用同一套规则，
避免两条渠道判定漂移。判定顺序：设备身份 → 设备-景区绑定 → 账户/关系 → 票状态冻结 →
政策生效期 → 景区覆盖 → 记名要求 → 权益窗口 → 营业/闭园 → 剩余次数。

## 3. 票的生命周期：只作用于“尚未消费的对应权利”

| 变化 | 对权益的影响 |
| --- | --- |
| 记名 `TICKET_NOMINATED` | 当前持票令牌更换；各权利项剩余次数平移到新令牌 |
| 转赠 `TICKET_TRANSFERRED` | 同批 `BENEFIT_ADJUSTED(TICKET_TRANSFERRED)`：旧令牌按剩余次数扣减、新令牌补发；已消费记录留在原令牌名下 |
| 退票 `TICKET_REFUNDED` | 同批 `BENEFIT_REVOKED`：冻结全部剩余权利；已核销照常参与清算 |
| 作废 `TICKET_INVALIDATED` | 同上（防伪失败等） |
| 比赛延期 `MATCH_POSTPONED` | 对所有未终结账户发 `BENEFIT_ADJUSTED(MATCH_POSTPONED)`，窗口按开赛时间差整体平移 |
| 景区临时闭园 `SPOT_CLOSED` | 闭园区间内核销拒绝；损失可经申诉 `BENEFIT_ADJUSTED(SPOT_CLOSURE/APPEAL_GRANTED)` 补偿 |

票务事件与权益事件放在**同一提交批**里，避免出现“票退了、权益还能刷”的中间态。

### 转赠的隐私语义
受让方拿到的是剩余次数，但**看不到前手的历史行程**（历史核销的 `person_token` 仍是前手）。
前手已用掉某景区次数的效果仍然延续——该景区额度不会因转赠而“补回”。

## 4. 离线核销与合并

### 凭证（游客二维码）
- 平台 HMAC 签名信封：政策版本、范围、窗口、各景区条目；终端离线即可验明平台签发。
- **逐景区 AES-256-GCM 加密**：每个协议景区的条目用该景区专属密钥加密。终端只预置本景区密钥，
  只能解开本景区那一条。即便游客去过别的景区，终端也无法从“有无条目”推断行程（所有协议景区都有条目，
  额度用完时条目内 `remaining=0`）。
- 条目内只有：账户假名、人假名（均为该景区专属）、关系、权利项 ID、剩余次数。

### 终端（断网闸机）
- 设备必须先联网登记（`DEVICE_REGISTERED`），预置设备签名密钥与本景区条目密钥。
- 本地按 `device_seq` 记账，防止同一设备离线期间重复刷；受 `offline_quota` 总量限制。
- 每笔签发设备 HMAC 签名的待同步凭证（规范化串字段固定，防重排伪造）。
- 离线无法获取最新闭园公告与票务状态：这类冲突留到联网合并时按发生时点裁定。

### 同步合并（`sync-service`）
1. 设备身份与凭证签名校验，失败直接 `REDEMPTION_VOIDED(SIGNATURE_INVALID)`；
2. 平台用主密钥把景区假名解析回全局账户（在发生时点的模型上解析，兼容历史令牌）；
3. 全部待同步凭证按 `occurred_on_device_at → device_id → device_seq → proof_id` 排序；
4. 逐条在时点模型上跑 `evaluateEligibility`：
   - 合法 → `REDEMPTION_CAPTURED(channel=OFFLINE_SYNC)`，金额取当时政策条款价；
   - `QUOTA_USED` → 时间线上输掉竞争：同刻为 `QUOTA_CONFLICT`，否则 `DOUBLE_SPEND`，作废但**可申诉**；
   - 其他规则不满足 → `REDEMPTION_REJECTED`（同样带版本与依据）；
5. `pending_proof_id` / `client_key` 幂等，重复同步不重复入账。

## 5. 清算：为财政生成可回查的补贴

- 月末 `CLEARING_BATCH_OPENED` 圈定周期；`settleBatch` 把周期内**已核销、未在册**的凭证逐笔生成
  `CLAIM_SETTLED`，每条都有金额快照、政策版本、设备、票介质与计价时票务状态快照——财政凭事件补贴。
- 一条核销凭证最多入账一次；曾入账并被冲正的不会被再次结算。
- `ENTRY_REVERSED` 记负数，可选择 `restoreQuota` 回补游客权益（申诉属实时）。
- 批次关闭汇总应收 / 冲正 / 净额。
- `audit.traceEntry` 提供补贴 → 核销事件（含离线来源与设备签名锚点）→ 设备 → 政策版本 →
  票根真实当前状态 → 后续调整/冲正/申诉的全链路回查。

## 6. 隐私分级

| 角色 | 可见 | 不可见 |
| --- | --- | --- |
| 游客（本人令牌） | 名下全部账户、各景区剩余权益、完整行程、每次拒绝依据、作废与申诉 | — |
| 景区 | 仅本景区核销、本景区专属假名、待结算金额、被冲正记录 | 身份、其他景区行程、其他景区是否到访 |
| 清算 | 金额、政策版本、设备、票介质、计价时状态、**清算假名** | 票号、身份、行程明细 |
| 主管部门 | 授权下全链路回查（持主密钥可还原假名映射） | — |

三套标识互不相同、不可互推：持票人全局令牌（仅平台/游客）、景区假名
（`HMAC(secret, "person:<spotId>" | token)`，同游客不同景区不同）、清算假名
（`HMAC(secret, "clearing" | accountId)`）。证据材料正文不进事件流，只存 SHA-256 指纹与类型。

## 7. 扩展与运维注记

- 存储当前为内存 `EventStore`；事件形状即落库形状，可平移到追加型日志（Kafka/表存储），
  投影改为订阅增量。
- 密钥（平台签名、景区条目主密钥、设备密钥、令牌主密钥）演示期内置默认值，生产必须接入 KMS
  并通过 `createApp({ secrets })` 注入；设备密钥与景区密钥带外分发。
- HTTP 层的 `x-client-role` 仅用于联调，生产由网关完成身份认证与渠道隔离。
- 政策新增条款时优先新增事件/枚举并在 `$defs` 记录载荷语义，保持旧消费者忽略未知字段的兼容性。
